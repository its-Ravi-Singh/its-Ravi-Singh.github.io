Offline RL: Decision Transformer with Preference Learning

Graduate Deep Learning & RL capstone · D4RL / Minari Hopper · PyTorch
Complete

Offline reinforcement learning for MuJoCo continuous control, treating RL as a sequence-modelling problem. I trained a Decision Transformer on fixed Hopper trajectories with no online environment interaction, then built an RLHF-style preference pipeline on top to test whether preference signals can steer offline policy training — and what happens when those labels are noisy or wrong.

What I built

  • A causal Decision Transformer (726K params, 3 layers, 4 heads) over return-to-go, state and action tokens, trained with a masked-MSE action objective.
  • A Perceiver-style comparison policy (1.9M params, learned latent tokens and cross-attention) seeing only the current state and target return — no history buffer.
  • A Bradley–Terry preference model scoring trajectory segments, trained on 2,000 generated pairs to 91% validation accuracy, then used to reweight Decision Transformer training windows.
  • An error-analysis pass flagging high-confidence wrong preference predictions — the failure mode that matters, since those push training hardest in the wrong direction.
  • A Gradio demo with live action prediction and recorded Hopper rollouts.

The two policies, running

Three-way Hopper-v4 benchmark

SplitModelAvg returnRelative
SimpleDecision Transformer60.4
SimpleDT + Preference76.2
SimplePerception Transformer593.5
MediumDecision Transformer24.0
MediumDT + Preference67.4

ExpertDT + Preference88.3

Preference weighting improved the Decision Transformer on all three splits — largest on medium (24.0 → 67.4), and on expert it produced the best policy overall. But the much simpler one-step Perception Transformer dominated on simple and medium. That's the genuinely interesting result: under a bounded training budget, the architecture that needs no history was far easier to train than the one that reasons over it.

Scope, stated plainly: 10 epochs, a bounded 10,000-sample budget per split, 5 evaluation episodes, single seed, no hyperparameter tuning. Directional results, not a tuned benchmark — the repo's report says so and lists seed averaging as the first fix.

Warehouse Robot Navigation — Q-Learning vs SARSA

Custom RL environment · tabular TD control · NumPy, no RL libraries
Complete

I wrote the environment rather than using a pre-built one — a 6×6 warehouse where a robot collects an item and delivers it past shelves, with optional stochastic transitions. Then I implemented Q-Learning and SARSA from scratch to compare on-policy against off-policy control on a problem small enough (72 states) to reason about exactly.

This is the trained agent's actual greedy trajectory, replayed step for step from the saved Q-table: five moves left to the pickup, then down and around the shelves to the drop. 18 steps, +107 reward — the optimum for this layout.

500 episodes, averaged over 5 seeds

EnvironmentAlgorithmRewardEpisodes to 90%Shorter = faster
DeterministicQ-Learning107.073
DeterministicSARSA107.0114
StochasticQ-Learning105.279
StochasticSARSA105.2135

Both algorithms converged to the identical optimal policy; Q-Learning got there roughly 1.6× faster. But the textbook result — that SARSA learns a safer path — did not appear at all, and I expected it to.

My explanation: the environment had no cliff. Hitting a shelf costs reward but the episode continues, so there is nothing catastrophic for an on-policy learner to be careful about. To test that, I added a mode where collisions are terminal and reran everything. SARSA then collided 37% less often during training (0.069 vs 0.109 per episode) while both still converged to the same collision-free policy — the caution shows up exactly where the theory says it should.

A bug worth recording: my reset() reseeded the RNG every episode, so every episode drew identical random numbers. Nothing crashed and the curves looked fine — the results were just meaningless. Fixed, and documented in the repo rather than quietly patched.

Retinal OCT Classification — Interpretability & Deployment

OCTMNIST · PyTorch CNNs · coursework, University at Buffalo
Complete

Four-way classification of retinal OCT scans — choroidal neovascularization, diabetic macular edema, drusen, normal. A baseline CNN, then an improved one. The useful part was reading past the headline accuracy.

What I built

  • A baseline CNN (896K params) and an improved version (1.7M) adding BatchNorm, class-weighted loss, weight decay, LR scheduling and early stopping. Test accuracy 71.2% → 76.5%.
  • Interpretability via PyTorch forward hooks — capturing activations at early, middle and late convolutions, plus the learned first-layer kernels.
  • A generated, self-contained deployment folder running a Gradio inference app.

Per-class recall — improved model

ClassPrecisionRecallRecall
Choroidal neovascularization0.660.95
Diabetic macular edema0.890.89
Drusen0.970.29

Drusen recall is 0.29. The model misses seven in ten cases of that condition while reporting 76.5% overall. Its precision on drusen is 0.97 — it is almost always right when it makes the call, it just almost never makes it. In a clinical setting, sending 69 drusen patients away as normal is the failure that matters, not the aggregate number.

The validation score was misleading. The improved model scored lower on validation (0.9049 vs 0.9139) yet higher on test. Validation follows the imbalanced training distribution; the test set is balanced at 250 per class. Selecting on validation accuracy would have made me keep the worse model — which is also most of why the baseline drops from 91% to 71%.

Deep Q-Networks — DQN vs Double DQN

Three control environments · PyTorch · matched hyperparameters
Complete

Both algorithms written from scratch — replay buffer, target network, epsilon-greedy schedule — and run head to head under identical settings. Double DQN exists to fix one thing: standard DQN uses the same network to pick the best next action and to score it, and a max over noisy estimates is biased upward. The question I actually wanted answered was when that fix matters.

Greedy policy, true reward, mean over 10 episodes

EnvironmentDQNDouble DQNOutcome
GridWorld6.004.40plain DQN wins
CartPole500.0500.0both solved
MountainCar−112.7−101.0only Double DQN solved

Double DQN is not uniformly better. It solved MountainCar where plain DQN couldn't — sparse reward, long horizon, exactly where overestimation compounds. Both saturated CartPole. But on a small tabular GridWorld with dense reward it scored lower, because a deliberately conservative target just slows early value propagation when there was no bias problem to fix. The correction pays off in proportion to how much overestimation was actually hurting.

The repo logs the mean target-network value estimate on every training step, so the overestimation gap between the two agents can be measured rather than asserted.

Neural Network from Scratch — NumPy to PyTorch

Backpropagation by hand · self-directed · Dec 2025 – Jan 2026
Complete

Build the same network twice. First in pure NumPy — forward pass, chain-rule backpropagation, BCE and MSE losses, SGD, all derived by hand with no autograd. Then rebuild the identical architecture with torch.nn.Module.

The part that matters

  • Both implementations receive identical inputs and identical initial weights, and their gradients are compared elementwise. They match.
  • That check is what separates "I implemented backpropagation" from "I implemented it correctly" — it catches the failure where a sign error or a missing transpose still produces a loss curve that goes down, just to the wrong place.
  • Trained on MNIST digits, with the NumPy version writing its own parameter initialisation and forward and backward passes end to end.

Anyone can call .backward(). Debugging a run that isn't converging is guesswork if that call is a black box — knowing the gradient into a sigmoid saturates when its input is large, because I derived that term myself, is the difference between "try a lower learning rate" and knowing where to look.

MODI — Location Review Database Schema & Queries

PostgreSQL · Supabase · CSE 560 DMQL course, Spring 2026 · Team project
Complete

A normalized PostgreSQL database for a location review system: users discover places, save favorites, leave reviews, and report bad entries. Twelve-table schema across geography, venues, and user activity, with trigger-based audit logging. Built and deployed on Supabase during the Spring 2026 Data Models and Query Languages course.

Database schema

Schema breakdown

  • Geography cascade: state → city → postal_zone → area, establishing spatial hierarchy for venue placement.
  • Venues: places table bridges geography and categories, with composite indexes on (area_id, category_id) for fast discovery.
  • User lifecycle: users table with composite primary key (id, user_id); login_data tracks activity; favorite_place, review, report capture interactions.
  • Audit by trigger: review_error_log is server-fed via database trigger on failed review inserts — validation errors logged automatically.
  • Referential integrity: 11 foreign keys enforce consistency; 12 primary keys (one composite) define identity.

Performance & queries

Team implemented indexing strategy (B-tree on PKs, composite on frequently-filtered columns), schema creation scripts, and data-loading pipelines. Query plan analysis showed measurable gains in lookup latency on the places table — especially for the common (area_id, category_id) filter pattern.

Authenticity proof: Live Supabase server timestamps show this was built in Spring 2026. login_data.last_login spans Apr 19 – May 2 (301 rows, logged at 16:51:52 to 05:44:32). review_error_log captures two trigger-fired entries Apr 26, 22:10:47 – 01:42:09. Not seeded data — written by the running application and database at runtime.
